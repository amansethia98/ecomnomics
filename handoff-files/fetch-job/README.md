# Nightly fetch job (box side), built 14 Nov 2026 against main 5aea5627

Run: `python3 run_night.py --restaurant restaurants/<slug>.json [--date D] [--reasons scheduled,...] [--platforms ...] [--probe-only]`
Owner-started history fill: `--from YYYY-MM-DD --to YYYY-MM-DD` (inclusive; `--to` is clamped to yesterday). Daily reports only, split into Zomato 30-day and Swiggy 7-day chunks. Same identity, sha, blank-day and AI-fallback checks as the nightly job. Use `--login-any-time` if a Swiggy session may need a password login outside 05:30–07:30 IST. Edge cases: BACKFILL-EDGE-CASES.md.

Tests (T1 + held/mismatch drills, INR 0): `python3 -m pytest -q tests`

Files
- run_night.py: orchestrator. preflight, computer status/boot/screenUrl (the fetch bot's own screen and profile), fetch-plan, 24 h mismatch count,
  session probe, recipes, local identity, sha check, upload, log-only rows, 3-mismatch stop, server hold (fetch-plan `held` / HTTP 423 fetch_held), summary.
- recipes.py: Z1/Z2 (Zomato business; Zomato payout settlement xlsx) and S1/S2 (Swiggy business: Download Report > brand > city > RID > Daily > Custom > Raise a Request).
  The Swiggy end date is clamped to the last day the calendar enables (about a 48 h lag). Z2: Finance > Payouts > past-cycle row > its download icon (picked by icon shape, never the mail icon). S2: Finance > Overview > Paid cycle card > See details > Payout Annexures. Payout xlsx go to /agent/v1/payout-reports as fileBase64. Weekly/monthly business views are not scripted yet.
- rakazo-fetch-snap: read-only helper copied into the computer at /opt/rakazo-fetch. It lists controls with their visible text through rakazo-page-browser's own agent-browser session.
- identity_check.mjs + identity.py: the local precheck runs the repo's own @rakazo/contracts code (evaluateBusinessReport, parsePayoutWorkbook, checkObservedIdentity)
  in a throwaway `--network none` container of the app image.
- convert.py: Swiggy xlsx to CSV. scrub.py: log scrubber. logs/: jsonl and summaries (scrubbed; no page text or file contents).
- Downloads land in bots/<bot>/fetch-job/inbox inside the computer and are deleted after the server answers. The inbox is emptied at the start and end of every run.

## Payouts (added 15 Nov 2026, main 9b9ef034)

- Z2 label: window [ps, pe) is the row "DD Mon - DD Mon'YY" (last day inclusive). Row must say PAID. Clicks only the icon whose SVG shape is the
  Material download icon; the "Send report to mail" icon is refused. A not-yet-built report is generated by the same click (~30 s).

## Blank-day guard (added 15 Nov 2026 evening, "blankday")
- Why: Zomato's daily file downloaded 15 Nov 01:01 (and identically 06:00) had Sat 14 Nov as all zeros (orders 0, rating 0.00, online 0%):
  the day was not filled in yet. It was stored as real data and gave false "sales down 100%" alerts.
- blankday.py (no model, INR 0), daily reports only, both platforms (Zomato raw CSV, Swiggy converted CSV), by metric label only (generic).
  A date column is blank when every order / sales / rate cell is zero or empty (`all_zero`), or a rating cell is 0 with zero orders
  (`rating0_orders0`). Only days at most 3 days old (IST; env ECOM_BLANK_LAG_DAYS) are judged; an older all-zero day is a real closed day.
- run_night.do_window: blank columns are cut out of the CSV before the local identity check and upload; jsonl step `blank_day`
  result `not_in_yet` with the dates; summary result `blankDays`. The server stores the rest and records the cut day as a
  `missingPeriods` gap (nothing stored for it), so the scheduled 7-day window (then backfill) fetches it again next night.
  A trimmed file is matched/posted by content sha only (no rawSha256). If every day in the file is blank nothing is posted and no
  failure row is logged: result `status: not_in_yet, reason: blank_day`. Normal files are posted byte-for-byte as before.
- Zero rows already stored (Zomato 14 Nov, fetch cmwgsxprl06ya01quhiwqa66z, 51 rows): the next file that has the day with real numbers
  supersedes them through ingest's planReplaceWindow (changed values superseded + inserted). Tests: tests/test_blankday.py.

## AI fallback + learn (added 16 Nov 2026, "aifallback")
- Aman's rule: a fetch bot never just stops on a page step. Business reports (both platforms): scripted stages, up to 3 tries from a fresh
  page (ECOM_UI_TRIES) -> a promoted learned recipe for the failing stage (no model) -> the AI (aifallback.py; x-ai/grok-4.7 via OPENROUTER_API_KEY,
  Gemini refused) acts on the page from the start of that stage, one action per call, 15 actions max, INR 60 per window (ECOM_AI_CAP_INR),
  INR 150 per IST night across the 05:30 and 08:00 runs (ECOM_AI_NIGHT_CAP_INR; ledger logs/ai-spend/<date>.json).
- The AI never clicks Generate/Download. It says "ready". Then code checks that the page shows our restaurant or outlet and exactly the plan's range
  (the "Selected:" line, or the checked "Custom dd/mm/yyyy - ..." radio button), and code clicks. After download the usual identity check and server checks decide.
- Learned recipes: learned/<platform>_<report>.json (versioned, with history and evidence) and a readable .md. They're stored as templates
  ({range_dmy}, {outlet_name}, {brand}, {start_d}, "{*} Current week"...), never per restaurant. A recipe is promoted only after the presubmit, identity and
  upload checks all passed (stored/skipped). A replay failure or a wrong file marks it stale, and the AI then learns a new version.
- recipes.py: zomato_business / swiggy_business are now Recipe stage lists run by run_scripted (same steps and checks as before).
  ui.Page records clicks and fills while page.trail is a list.
- Still failing at 05:30: `retry: "08:00"`, entry in logs/retry-queue/<date>-<slug>.json, summary `alerts_deferred` (no alert yet).
  `run_night.py --retry-queue` (08:00) runs only the pending windows: resolved / failed_after_retry, summary `alerts`. An empty list exits before booting.
  Payouts: 3 scripted tries + the retry list (no AI for payouts yet). Reports that aren't scripted (Zomato monthly, Swiggy weekly/monthly) only use the AI with ECOM_AI_UNSCRIPTED=1.
- A signed-out page mid-window: the normal login path once (Swiggy only), then the window once more.
- AI transcripts: logs/ai-runs/ (action, role, templated control text and cost only). Edge cases + tests: AI-FALLBACK-EDGE-CASES.md, tests/test_aifallback.py.
- Live test 16 Nov 07:49 IST: Zomato Weekly 9-15 Nov, the pilot restaurant. The scripted step failed 3/3 (the weekly view has a week list, not a calendar). The AI took 6 calls (INR 7.66),
  checks passed, 47 rows stored (fetch ${FETCH_ID}), recipe learned (v2). The second pass at 07:55 replayed the recipe with no model (INR 0), got the same file and the sha check skipped it.
