# Zomato login compatibility boundary

## What is restored

`zomato_browser_246c11b.py` and `zomato_secrets_246c11b.py` are **unmodified Git blobs** from `246c11b`. Hash tests pin every byte, not just the key sender. While the HTTPS Zomato authentication page/frame is present, the current native entrypoint dispatches navigation, snapshots and ordinary actions to that complete old runtime. Its focus, code detection, event delivery, checks, field filling, snapshots, click/submission and error handling all come from the old files. Do not patch those frozen files.

The old successful conversation asked the owner to reply with the emailed code. It did not use `request_secret oneTimeCode` or `fill_code`: neither existed in that revision. The compatibility instructions restore the owner-reply path, ordinary `browser_act type`, and a separate visible Continue click if needed. A coordinator with explicit inbox permission may supply the owner reply. Never resend, replay, print or save the code.

**Privacy trade-off:** the code is model-visible in an ordinary conversation, as it was historically. This is not the newer masked/run-held code-card contract. No real codes or account details belong in tests, fixtures, source or diagnostic reports.

## Important limit on “exactly like before”

The native sources are byte-identical. The entire application and the model's decisions are not frozen. The old archived conversation retained tool names/outcomes, not the exact historical `browser_act` arguments. It therefore does **not** establish whether that successful attempt used one action or several.

The real captured DOM has six unlabelled sibling text inputs with `maxlength=2`, `inputmode=text`, and no OTP hints. The old helper's special cross-frame code routine recognizes only `maxlength=1`. With this actual layout, ordinary cross-frame `type` sends keyboard **insertText**, not per-character keydown/keyup events. Sending a whole six-character code to the first maxlength-two input is not sufficient in the offline fixture: it keeps two characters in the first box. The fixture deliberately does not contain a magic distributor that would hide this failure.

For those six boxes the instructions use **one batch of six ordinary old `type` actions**, one character on each fresh box ref, followed by the old ordinary Continue click. This uses only mechanisms available in the old runtime, not a replacement segmented/private filler. The full entrypoint-to-submit test proves this works against the captured structure. It does not prove the exact unrecorded historical action sequence or reproduce unavailable production event handlers.

## Why the previous attempts failed

- The earlier generic secure filler required a maxlength-one box, or a maxlength-two box with recognisable code hints. These actual maxlength-two boxes have none. The retained pre-entry capture establishes a structural mismatch; it does not establish a stale ref.
- `1c0216777` replaced the lowest-level key sender but retained the new private-card request, per-box preparation/focus and strict isolated-world acceptance checks. It was not a rollback of the old login chain.
- The live result was `completed:0`, partial/uncertain. No submission or reconciliation followed. Once typing was marked touched, several different failures collapsed into that same error. Zero completed actions does not prove zero characters reached the page. Retained evidence has no failing-character trace or CDP exception. It cannot distinguish a failed focus/readiness/value check from node replacement or a lost browser reply; claiming one specific event would be speculation.

## Offline evidence

Run the computer unit suite normally. For the real-browser tests use a computer-test image with Chromium and the pinned agent-browser, `--network=none`, and `RAKAZO_BROWSER_OFFLINE_TEST=1`.

`test_legacy_code_browser.py` resolves the real auth hostname to local HTTPS inside the network-isolated container. It exercises the **current native entrypoint**, real cross-origin frame, actual refs, frozen ordinary typing, fresh result refs and an actual Continue click. It asserts six trusted input events, correct complete entry and a submitted boolean. Every fixture input's full reconstructed child-index path and attributes are asserted. The account-free JSON fixture also checks the complete field records retained in the original audit prefix independently. That prefix retains four complete fields and part of the fifth; the sixth field's repeated attributes/path are a reconstruction, not a retained complete audit. The separate snapshot establishes the total of six textboxes. Negative controls reject synthetic setter events, demonstrate the whole-code/maxlength-two failure, and refuse the private-code route without typing.

Only DOM structure was retained from the site; fixture event behavior is explicitly synthetic. Passing offline is not a claim that an unperformed live sign-in has succeeded. A fresh, separately authorized live check is still required after deployment; it must use a normal owner/coordinator reply, **not** the private-code-card delivery helper.

## Final requested scope

The final owner steering requested a direct maxlength-two matcher fix as well as the old login rollback, then requested **no further offline Chromium work**. The generic short-slot matcher therefore accepts maxlength 1 or 2 within the same validated group. The earlier offline Chromium results above describe tests already completed before that final steering; the last matcher edit receives only the requested fast unit/lint sanity check. No live success is claimed.
